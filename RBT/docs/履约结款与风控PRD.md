## 1. 需求描述

### 1.1 范围

本文约定贸易商支付完成、需求进入「门店付款中」之后，门店如何按日履行，各方如何结款，以及冷丰如何看进度和风险。

页面与原型：

* B 端首页：`RBT/rbt_index.html`。左侧菜单「首页」
* 履约：`RBT/rbt_performance.html`。菜单在「交易单」下方
* 每日履行：`RBT/rbt_daily_fulfill.html`
* 风控配置：`RBT/rbt_risk_config.html`
* 异常履约数据：`RBT/rbt_risk_abnormal.html`
* 门店端履约：丰银宝门店端内的 RBT 菜单，原型 `RBT/rbt_h5_store.html`
* 贸易商端收款：原型 `RBT/rbt_h5_trader.html`
* 服务商端收款：原型 `RBT/rbt_h5_provider.html`，入口在移动端首页「贸易商端」下方

左侧菜单顺序为「首页」「门店准入管理」「商品包」「产品配置」「需求单管理」「交易单」「履约」「每日履行」「风控配置」「异常履约数据」。

结算系数、渠道结算比例的配置页仍以《产品配置PRD》为准。需求状态、合同、交易单仍以《需求单管理PRD》《交易单PRD》为准。本文不改那些页面的原规则，只约定进入门店付款中之后的履行和结款。

用语：页面和本文写「履约」「支付」「结款」。不写「还款」「借贷」。需求状态仍是「门店付款中」，履约页和收款页展示为「履约中」。历史状态「还款中」与「门店付款中」同一口径。

### 1.2 主链路

待审核 → 待接单 → 待确认签约 → 待签署 → 待付款 → 门店付款中 → 已完成

履行从「门店付款中」开始，到「已完成」结束。

* 贸易商在线支付，或确认线下支付后，需求变为「门店付款中」。此时生成上游交易单、下游交易单、冷丰服务费单，规则见《交易单PRD》。履约、每日履行不再生成这些单据
* 只有结算方式为「比例付」才产生每日履行和三方应收。其他结算方式不预造履行行
* 门店付款中期间，每个已经发生的营业日按渠道从营业收入自动扣款。门店也可以对剩余履行额做一键履约。一键履约单独成行，不替换当天的自动扣款
* 剩余履行额为 0 时，履约阶段为「已完成」。各端不能在履约页或收款页把状态手改成已完成
* 待付款及之前不产生履行行，不进入履约列表，不进入收款列表
* 额度仍按《门店管理PRD》《需求单管理PRD》：门店付款中仍占用；已完成不再占用。本文不另改额度

### 1.3 各方应收

取值起点是需求上的商品金额。系数先保留两位小数，再乘商品金额，四舍五入到分。缺商品金额、缺系数，或结算方式不是比例付时，三方应收不计算，相关金额展示「—」。

* 门店实付 = 商品金额 × 门店结算系数。需求总金额与此一致，也等于商品金额 + 服务费
* 贸易商所得 = 商品金额 × 贸易商结算系数。这是贸易商整单应收。贸易商服务费 = 贸易商所得 − 商品金额
* 服务商计提 = 商品金额 × 服务商结算系数 − 商品金额。只取系数超出 1 的部分
* 冷丰实得 = 门店实付 − 贸易商所得 − 服务商计提
* 本单应收 = 贸易商所得 + 冷丰实得 + 服务商计提。比例付下等于门店实付

待审核时按产品配置计提服务商。初审通过后，只有需求上确认了服务商才计提。没有服务商时，服务商计提为 0，这部分留在冷丰实得，该需求不出现在服务商收款。

从待接单到门店付款中，可以只改这一单的渠道结算比例，不改产品上的结算系数。规则见《需求单管理PRD》。

例：商品金额 ¥750.40，门店系数 1.60，贸易商系数 1.20，没有服务商。门店实付 ¥1,200.64，贸易商应收 ¥900.48，冷丰实得 ¥300.16，服务商应收 ¥0.00。

### 1.4 每日自动履行

只生成已经发生的营业日。一天、一个渠道一行。未发生的日期不出现。

* 营业流水：该渠道当日门店实际营业额。无值展示「—」
* 所得佣金：当日该渠道已发生的门店佣金。无值展示「—」
* 应履行 = 所得佣金 × 该渠道结算比例，四舍五入到分
* 自动扣款的实际履行等于应履行
* 支付方式：营业收入自动扣款
* 计算来源：获准营业事实。这个字段说明金额从已发生营业算出，不是支付方式
* 渠道只有 POS、直播、商城。用需求单上该渠道的结算比例。POS 的堂食、外卖、团购不另起行，仍用 POS 这一渠道的比例
* 结算比例在页面写成「POS 10.00%；直播 10.00%；商城 10.00%」。该单比例不同时，按单上的比例显示，例如 8.00%。没有比例时展示「—」

结算单在营业日的次日 08:00:00 确定。

* 履约中：已发生营业日里最近一天记「预计履行」，结算时间展示「未执行」。更早的日期记「已履行」，结算时间为营业日次日 08:00:00
* 同一天多个渠道，预计履行金额相加
* 整笔变为已完成后，原来那条预计履行改记「已履行」，行和金额保留。基础信息里的预计履行显示「无」
* 还没有营业流水时，不预造金额。门店基础信息的计算来源写「还没有营业流水」，预计履行写「未计算」，应履约写「未产生」

### 1.5 一键履约

门店对剩余履行额主动支付。只对剩余履行额大于 0 的需求开放。没有可付需求时，按钮置灰。

* 先选履约需求。只有一笔时直接带出单号，多笔时下拉选择，选项带剩余履行额
* 履约金额大于 0，最多两位小数，不能超过该单剩余履行额。超过时改回剩余履行额。未填或格式不对时提示「请填写履约金额，最多两位小数」；小于等于 0 时提示「请填写大于 0 的履约金额」
* 支付方式为支付宝或微信，默认支付宝
* 确认后输入 6 位支付密码。未设置密码时提示「请先设置支付密码」，不进入支付。密码错误在页内提示剩余次数。连续错误 4 次锁定当日，提示后关闭，不扣款。点遮罩或关闭，不支付
* 支付成功后单独增加一行。渠道展示「一键履约」，支付方式为所选的支付宝或微信，计算来源为「手动履约」。营业流水、所得佣金为空，结算比例为「—」。应履行和实际履行都等于支付金额。结算时间、结款时间都用实际支付时间
* 这一笔立刻计入门店已履行，并按 1.6 单独拆给三方。不并进当天自动扣款，也不占用「最近一个营业日结算单未确定」的位置
* 本期不校验账户余额，不做「账户余额不足」

### 1.6 三方拆分

每一笔实际履行按贸易商所得、冷丰实得、服务商计提的占比拆开。

* 三笔之和等于该笔实际履行
* 除应收最大的一方外，按分向下取整。尾差归应收最大的一方
* 营业日的多笔放在同一段里分摊，尾差落在最近一个已发生营业日
* 一键履约单独拆，不把营业流水的尾差放进这一笔
* 没有服务商时，服务商结款为 0。拆给某一方为 0 的一键履约，不出现在该方结款明细
* 冷丰收款方名称为「上海冷丰科技有限公司」

门店点开一行时，用同一套构成展示，只显示权重大于 0 的项。除最后一项外按分向下取整，尾差归最后一项。四项之和等于这一行金额。

* 商品金额，权重为商品金额
* 贸易商服务费，权重为贸易商所得 − 商品金额
* 冷丰服务费，权重为冷丰实得
* 服务商服务费，权重为服务商计提

商品金额 + 贸易商服务费 = 贸易商所得对应的份额。

沿用 1.3 的例子，一键履约 ¥100.00：贸易商 ¥75.00，冷丰 ¥25.00，服务商 ¥0.00。门店明细为商品金额 ¥62.50、贸易商服务费 ¥12.50、冷丰服务费 ¥25.00。

### 1.7 整单金额与履约阶段

* 待付总额：有商品金额或服务费时取两者之和；都没有时取总金额。比例付下与总金额一致
* 已履行金额 = 已发生日期的实际履行合计，含一键履约
* 剩余履行额 = 总金额 − 已履行金额。门店端用待付总额减已履行金额。小于 0 时取 0
* 履约阶段：状态为门店付款中且剩余履行额大于 0，展示「履约中」。剩余履行额为 0，或需求状态为已完成，展示「已完成」
* 已完成时，履约列表和履约详情的已履行金额取总金额，剩余履行额取 ¥0.00，日均履行进度和履约风险等级展示「—」
* 首页「当前履约中」只保留剩余履行额仍大于 0、且已有每日履行的门店付款中需求。已完成不在这张表

金额保留两位小数，前面加 ¥。无值展示「—」。门店履约页顶部的剩余履行额使用千分位。

### 1.8 结款

贸易商应收取贸易商所得。服务商应收取服务商计提。冷丰收款取冷丰实得，在每日履行和履约详情里与另外两方一起展示。

履约中：

* 已结款 = 已确定营业日拆给该方的金额 + 一键履约拆给该方的金额。最近一个营业日不计入
* 待结款 = 应收 − 已结款。还没有已结款时，已结款按 0。没有应收时不计算，展示「未产生」或「—」
* 卡片和基础信息上的待结款，是整单还没结给该方的余额。结款明细里标成「待结款」的一行，只表示最近一个营业日的结算单还没确定，金额是这一天拆给该方的份额。两个数字各算各的

已结束（已完成、已作废、已驳回）：

* 有应收时，已结款等于应收，待结款为 ¥0.00
* 结款明细仍只列已经发生的份额，全部标「已结款」。各行之和可以小于应收，不另补一行凑齐

结款状态和结款时间：

* 最近一个已发生营业日，且需求未完成：待结款，结款时间写「-」
* 更早的营业日：已结款，结款时间写营业日次日 08:00:00，展示到月日时分秒
* 一键履约：已结款，结款时间写实际支付时间
* 需求已完成：明细行全部为已结款

列表顶部的笔数、应收、已结款、待结款，是当前页签内各卡片同名字段相加。没有应收时顶部应收展示「—」。没有已结款时展示「未产生」。履约中没有待结款时展示「未产生」；已结束没有待结款时展示「无」。

### 1.9 日均履行进度与风险等级

只看已发生日期。同一天多个渠道先把实际履行加总，这一天合计为 0 才算未履行。

* 连续未履行天数：从最近一个已发生日期往前数，实际履行为 0 的日期连续累加，遇到大于 0 的日期停止
* 最近未履行日期：这段连续天数里最近的那一天。天数为 0 时展示「—」
* 已履约天数：最早已发生日期到最晚已发生日期的自然日，含首尾。中间没有流水的日子也算进去
* 累计履行进度 = 已发生实际履行合计 ÷ 本单应收
* 日均履行进度 = 累计履行进度 ÷ 已履约天数。页面按百分比保留两位。算不出时展示「—」

评级先看异常，再看预警，再看关注。多档同时命中取更重的一档。每一档单独选择条件关系。

* 「或」：连续未履行天数、日均履行进度满足一个即命中
* 「且」：两个都要满足

未满进度起算天数时，日均履行进度不参与命中，页面仍展示算出来的百分比。连续未履行天数仍然参与。未达到关注条件的等级是正常，不发异常提醒。

风控评级关闭后，全部记正常。异常履约数据为空。每日履行的金额不变。

默认：进入履约满 7 天起算日均。关注为连续 1 天，或日均低于 67%，提醒「提醒门店核对营业流水、所得佣金、结算比例」。预警为连续 3 天，或日均低于 40%，提醒「提醒门店、贸易商、冷丰；建议暂停该店新的需求」。异常为连续 7 天，或日均低于 20%，提醒「提醒门店、贸易商、冷丰、服务商；建议停止该店新的需求，并核对担保金缴纳凭证」。

异常提醒由这些内容接成一句：门店、需求单号、命中的连续天数或日均履行进度、剩余履行额，再接该档配置的提醒句。正常不提醒。

首页、履约列表、履约详情、异常履约数据里的已履行金额、剩余履行额、日均履行进度、履约风险等级用这一套。已完成在履约列表和履约详情改为 1.7 的完成口径。

### 1.10 首页

页签名「履约风险」。顶部说明：只按已发生日期评级；当日实际履行为 0 时从这一天往前连续计数；日均履行进度 = 累计履行进度 ÷ 已履约天数；未满起算天数不看日均；每档按风控配置选「或」「且」；多档同时命中取更重的等级；未发生的日期不参与。

顶部四张卡：正常、关注、预警、异常。数字是「当前履约中」里对应等级的笔数，没有则为 0。

当前履约中：

* 只收状态为门店付款中、已经有每日履行、剩余履行额仍大于 0 的需求
* 说明写在表上：剩余履行额 = 总金额 − 已履行金额。日均履行进度按每日履行台账和本单应收计算。未达到关注条件的，等级是正常，不发异常提醒
* 列：门店、需求单号、连续未履行天数、应履行、实际履行、剩余履行额、日均履行进度、履约风险等级、最近未履行日期
* 应履行 = 已发生各行应履行合计。实际履行 = 已发生各行实际履行合计，含一键履约。剩余履行额 = 总金额 − 实际履行
* 需求单号打开履约详情
* 无数据：暂无履约中的需求

异常提醒只列出当前履约中等级不是正常的需求。列：履约风险等级、异常提醒。没有时：暂无异常提醒。当前履约中的需求都未达到关注条件。

持续未履行时是评级样例，不改每日履行里的实际履行。

* 前三行沿用当前履约单已经发生的应履行、实际履行、剩余履行额，只把连续未履行天数分别看成 1 天、3 天、7 天
* 最后一行把日均履行进度压到异常线的八成，已履约天数取进度起算天数，应履行和实际履行按这个进度反推
* 列：情景、连续未履行天数、应履行、实际履行、剩余履行额、日均履行进度、履约风险等级、异常提醒
* 样例算出来仍是正常的，不进入异常履约数据

### 1.11 履约

只列出贸易商付款完成、处于履约中或已完成的需求。状态范围是门店付款中、历史状态还款中、已完成。点需求单号或「查看」打开履约详情。每日履行在基础信息右侧。

顶部说明写明：应履行按所得佣金乘该渠道结算比例；当日实际履行再按应收占比拆成贸易商、冷丰、服务商收款；日均履行进度、剩余履行额与首页同一套规则；不预造未发生的日期；剩余履行额为 0 时履约阶段为已完成。舍入和退款跨期本期不另定。

查询为包含匹配，不区分大小写。履约风险等级、履约阶段为精确匹配。条件可只填一部分。

* 需求单号
* 门店：名称或门店编码
* 贸易商
* 服务商
* 收款账户名称：只搜索，不出现在表上。命中该单任一收款账户名称
* 收款账户：只搜索，不出现在表上。命中该单任一收款账号
* 履约风险等级：正常、关注、预警、异常
* 履约阶段：履约中、已完成。按展示阶段过滤，不按底层状态原文过滤

列表列：需求单号、门店、门店编码、贸易商、服务商、总金额、已履行金额、剩余履行额、日均履行进度、履约风险等级、结算周期、结算方式、履约阶段、更新时间。操作列「查看」。分页默认每页 20 条。无值展示「—」。无数据为空表。

履约中的已履行金额、剩余履行额、日均履行进度、履约风险等级与首页同一行需求相同。已完成时已履行金额取总金额，剩余履行额 ¥0.00，日均履行进度和履约风险等级为「—」，履约阶段为已完成。

履约详情的履行汇总：

| 字段 | 取值 |

## 4. 验收标准

共用口径：

* 比例付以外的需求不产生每日履行，不产生三方应收
* 待付款及之前的需求不在履约列表、不在收款列表、不在首页当前履约中
* 未发生的日期不出现在每日履行

各方应收与拆分：
