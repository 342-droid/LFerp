## 1. 需求描述

### 1.1 范围

本文约定贸易商支付完成、需求进入「门店付款中」之后，门店如何按日付款，各方如何结款，以及冷丰如何看进度和风险。

页面与原型：

* B 端首页：`RBT/rbt_index.html`。左侧菜单「首页」
* 付款：`RBT/rbt_performance.html`。菜单在「交易单」下方
* 每日付款：`RBT/rbt_daily_fulfill.html`
* 风控配置：`RBT/rbt_risk_config.html`
* 异常付款数据：`RBT/rbt_risk_abnormal.html`
* 门店端付款：丰银宝门店端内的 RBT 菜单，原型 `RBT/rbt_h5_store.html`
* 贸易商端收款：原型 `RBT/rbt_h5_trader.html`
* 服务商端收款：原型 `RBT/rbt_h5_provider.html`，入口在移动端首页「贸易商端」下方

左侧菜单顺序为「首页」「门店准入管理」「商品包」「产品配置」「需求单管理」「交易单」「付款」「每日付款」「风控配置」「异常付款数据」。

结算系数、渠道结算比例的配置页仍以《产品配置PRD》为准。需求状态、合同、交易单仍以《需求单管理PRD》《交易单PRD》为准。本文不改那些页面的原规则，只约定进入门店付款中之后的付款和结款。

用语：页面和本文写「付款」「支付」「结款」。不写借贷类用词。需求状态仍是「门店付款中」，付款页和收款页展示为「付款中」。

### 1.2 主链路

待审核 → 待接单 → 待确认签约 → 待签署 → 待付款 → 门店付款中 → 已完成

付款从「门店付款中」开始，到「已完成」结束。

* 贸易商付完货款，并且发货已确认，需求变为「门店付款中」后才开始每日付款。此时生成上游交易单、下游交易单、冷丰服务费单，规则见《交易单PRD》。付款、每日付款不再生成这些单据
* 只有结算方式为「比例付」才产生每日付款和三方应收。其他结算方式不预造付款行
* 门店付款中期间，按钱包实际入账日归集应付。商城、内部直播取已经入账的佣金；POS 取经营流水扣除平台服务费后的收款。各自再乘该渠道结算比例。日切冻结本批应付，次日同一付款批次分别向冷丰和贸易商转账，到账后才核销。提前支付单独成行，不替换当天的自动扣款
* 剩余付款额为 0，且没有待冻结、在途或未完成冲正时，付款阶段为「已完成」，并释放额度。各方还没到账的份额继续单独跟踪。各端不能在付款页或收款页把状态手改成已完成
* 待付款及之前不产生付款行，不进入付款列表，不进入收款列表
* 额度仍按《门店管理PRD》《需求单管理PRD》：门店付款中仍占用；已完成不再占用。本文不另改额度

### 1.3 各方应收

取值起点是需求上的商品金额。系数先保留两位小数，再乘商品金额，四舍五入到分。缺商品金额、缺系数，或结算方式不是比例付时，三方应收不计算，相关金额展示「—」。

* 需求单商品金额仍是原价。贸易商服务费并进单价，加价率 = 贸易商结算系数 − 1，由合同约束，页面不再单列「贸易商服务费」
* 订单实付 = 原价 ×（1 + 加价率）。进入订单和付款后，总金额、剩余应付都用含加价的实付
* 门店实付 = 商品金额 × 门店结算系数。冷丰服务费、服务商服务费仍按结算系数从实付里拆，不跟贸易商服务费一起藏进单价
* 贸易商所得 = 商品金额 × 贸易商结算系数。这是贸易商整单应收
* 服务商计提 = 商品金额 × 服务商结算系数 − 商品金额。只取系数超出 1 的部分
* 冷丰实得 = 门店实付 − 贸易商所得 − 服务商计提
* 本单应收 = 贸易商所得 + 冷丰实得 + 服务商计提。比例付下等于门店实付

待审核时按产品配置计提服务商。初审通过后，只有需求上确认了服务商才计提。没有服务商时，服务商计提为 0，这部分留在冷丰实得，该需求不出现在服务商收款。

从待接单到门店付款中，可以只改这一单的渠道结算比例，不改产品上的结算系数。规则见《需求单管理PRD》。

例：商品金额 ¥750.40，门店系数 1.60，贸易商系数 1.20，没有服务商。门店实付 ¥1,200.64，贸易商应收 ¥900.48，冷丰实得 ¥300.16，服务商应收 ¥0.00。

### 1.4 每日自动付款

应付按渠道分开算。商城、内部直播用已经入账的佣金。POS 用经营流水扣除平台服务费后的收款，演示里平台服务费按经营流水的 10% 计。再各自乘该渠道结算比例。后台一天、一个渠道一行。还没入账的日期不出现。门店端把同一天的 POS、商城、直播合成一条，标题仍写「当日支付」，不展示渠道结算比例。经营页仍按营业额展示 POS。

列表上的日期仍是原营业日。归集和付款批次用钱包实际入账日，两个日期可以不同。佣金在 26 日入账，就归 26 日日结，26 日日切冻结，进入 27 日付款批次。

* 营业流水：原营业日该渠道营业额，供经营和追溯。无值展示「—」
* 所得佣金：商城、直播为已入账佣金。POS 为经营流水扣除平台服务费后的收款。无值展示「—」
* 应付款 = 上述金额 × 该渠道结算比例，四舍五入到分
* 实际付款在该批次转账成功并核销后才等于应付款。已冻结、在途还没有实际付款
* 支付方式：营业收入自动扣款
* 计算来源：获准营业事实。这个字段说明金额从已入账营业算出，不是支付方式
* 渠道结算比例的页面文案仍是「POS 10.00%；直播 10.00%；商城 10.00%」。该单比例不同时按单上的比例显示。POS 的堂食、外卖、团购不另起行，仍算进当天 POS
* 应报未报记缺数据，不生成 0 元应付行。当天没有这个渠道的营业，不算缺报

日切和付款批次：

* 日切时按需求算出本批应付，并按 1.6 拆分。同一需求、同一次日切合成一个付款批次
* 批次里冷丰和贸易商各一条转账。钱包在同一事务预占这两笔。服务商份额不进这两笔转账，由财务另定路径；页面上仍算出服务商份额
* 冻结从可用余额扣出。转账成功才从资金桶扣减并核销
* 余额不足时整批留待冻结，不部分预占。之后只执行预占成功的批次
* 两条转账各自执行。一条成功就核销这一条，另一条在途继续冻结。确认未扣款并终止时，释放该条预占
* 多笔需求共用同一钱包时，先按合同约定顺序；合同没约定，按进入门店付款中的时间先后。每笔同时受本单剩余应付和可扣总额限制
* 日切时点跟随 BMS，不把 08:00 写成结算规则。结算时间、结款时间展示该笔实际到账时间。还没到账写「未执行」或「-」
* 已经入账却没被日结采到，是对账异常，不当成没有营业
* 渠道比例从下一入账日生效。已日切后的退款、差额另记调整，引用原订单、日结和付款
* 每一日按 1.6 拆。整单最后一笔再对齐各方应收上限
* 还没有入账时不预造金额。门店基础信息的计算来源写「还没有营业流水」，预计付款写「未计算」，应付款写「未产生」

付款中，最近一个入账日通常还在冻结或在途，这一天不是已付款。更早并且已经到账的日期记已付款。需求变成已完成后，没到账的批次保持原状态，不改记已付款。

### 1.5 提前支付

门店对剩余应付金额主动支付。只对剩余应付金额大于 0 的需求开放。没有可付需求时，按钮置灰。按钮文案「提前支付」。

* 先选付款需求。只有一笔时直接带出单号，多笔时下拉选择，选项带剩余付款额
* 付款金额大于 0，最多两位小数，不能超过该单剩余付款额。超过时改回剩余付款额。未填或格式不对时提示「请填写付款金额，最多两位小数」；小于等于 0 时提示「请填写大于 0 的付款金额」
* 支付方式为支付宝或微信，默认支付宝
* 确认后输入 6 位支付密码。未设置密码时提示「请先设置支付密码」，不进入支付。密码错误在页内提示剩余次数。连续错误 4 次锁定当日，提示后关闭，不扣款。点遮罩或关闭，不支付
* 支付成功后单独增加一行。渠道展示「提前支付」，支付方式为所选的支付宝或微信，计算来源为「提前支付」。营业流水、所得佣金为空，结算比例为「—」。应付款和实际付款都等于支付金额。结算时间、结款时间都用实际支付时间
* 这一笔立刻核销，并按 1.6 单独拆给三方。不并进当天自动扣款，也不占用当天日切批次的位置。与自动扣款共用该需求的剩余应付
* 提前支付计入日均付款额的分子。它不单独增加营业日。落在已确认营业日上时，并进这一天的实际付款，连续未付款在这一天停止。没有落在已确认营业日上时，只增加分子，不增加营业日天数，也不打断按营业日计算的连续未付款
* 本期不校验账户余额，不做「账户余额不足」

### 1.6 三方拆分

每一笔实际付款按贸易商所得、冷丰实得、服务商计提的占比拆开。

* 三笔之和等于该笔应分金额。已经到账的，三笔之和等于该笔实际付款
* 除应收最大的一方外，按分向下取整。尾差归应收最大的一方。并列最大时，尾差归该需求最后一笔已到账付款
* 每一日按上面的规则拆。整单最后一笔再对齐各方应收上限
* 提前支付单独拆，不把营业流水的尾差放进这一笔
* 没有服务商时，服务商结款为 0。拆给某一方为 0 的提前支付，不出现在该方结款明细
* 冷丰收款方名称为「上海冷丰科技有限公司」
* 自动批次只预占并转账冷丰和贸易商。服务商份额由财务另定执行路径，不进这两笔转账

后台仍按贸易商、冷丰、服务商拆。门店点开一行时不再单列贸易商服务费：货款展示贸易商所得（含加价），服务费展示冷丰实得 + 服务商计提。只显示权重大于 0 的项。除最后一项外按分向下取整，尾差归最后一项。

后台台账、每日付款、付款详情仍分开写冷丰、服务商，不跟门店端合并。

沿用 1.3 的例子，提前支付 ¥100.00：后台贸易商 ¥75.00，冷丰 ¥25.00，服务商 ¥0.00。门店明细为货款 ¥75.00、服务费 ¥25.00。

### 1.7 整单金额与付款阶段

* 待付总额：有商品金额或服务费时取两者之和；都没有时取总金额。比例付下与总金额一致
* 已付款金额 = 已经到账核销的实际付款合计，含提前支付。已冻结、在途不计入
* 剩余付款额 = 总金额 − 已付款金额。门店端用待付总额减已付款金额。小于 0 时取 0
* 付款阶段：状态为门店付款中且剩余付款额大于 0，或仍有待冻结、在途、未完成冲正，展示「付款中」。剩余付款额为 0 且没有这些在途时，展示「已完成」，并释放额度
* 已完成时，付款列表和付款详情的已付款金额取总金额，剩余付款额取 ¥0.00，日均付款额和付款风险等级展示「—」。各方已结款仍按实际到账计算，不改成应收
* 首页「当前付款中」只保留剩余付款额仍大于 0、且已有每日付款的门店付款中需求。已完成不在这张表

金额保留两位小数，前面加 ¥。无值展示「—」。门店付款页顶部的剩余付款额使用千分位。

### 1.8 结款

贸易商应收取贸易商所得。服务商应收取服务商计提。冷丰收款取冷丰实得，在每日付款和付款详情里与另外两方一起展示。

付款中：

* 已结款 = 已经到账核销、拆给该方的金额 + 提前支付拆给该方的金额。已冻结、在途不计入
* 待结款 = 应收 − 已结款。还没有已结款时，已结款按 0。没有应收时不计算，展示「未产生」或「—」
* 卡片和基础信息上的待结款，是整单还没结给该方的余额。结款明细里标成「待结款」的一行，只表示这一天的批次还没到账，金额是这一天拆给该方的份额。两个数字各算各的

已结束（已完成、已作废、已驳回）：

* 已结款仍只计已经到账的份额，不改成应收。待结款 = 应收 − 已结款
* 结款明细只列已经发生的份额。已到账标「已结款」，没到账仍标「待结款」。不另补一行凑齐应收

结款状态和结款时间：

* 还没到账的批次：待结款，结款时间写「-」
* 已经到账的批次：已结款，结款时间写实际到账时间，展示到月日时分秒
* 提前支付：已结款，结款时间写实际支付时间
* 需求已完成时，没到账的行不改成已结款

列表顶部的笔数、应收、已结款、待结款，是当前页签内各卡片同名字段相加。没有应收时顶部应收展示「—」。没有已结款时展示「未产生」。付款中没有待结款时展示「未产生」；已结束没有待结款时展示「无」。

### 1.9 日均付款额与风险等级

只看已经确认结果的营业日。缺报、已冻结、在途整日跳过，不进入分子，也不进入分母，更不能当成未付款。确认结果里实际付款为 0，这一天才算未付款。日均付款额是金额，不按百分比进度展示。

* 连续未付款天数：从最近一个已确认营业日往前数，实际付款为 0 的日期连续累加，遇到大于 0 的日期停止。缺报和在途不参与这串天数
* 最近未付款日期：这段连续天数里最近的那一天。天数为 0 时展示「—」
* 营业日天数：已确认结果的营业日天数。缺报、在途和中间没有流水的日子不计入
* 单店日均付款额 =（已确认营业日的实际付款合计 + 提前支付）÷ 营业日天数。算不出时展示「—」。和阈值比较时用未四舍五入的计算值
* 当前生效基准只取一种，页面写明「静态基准」或「动态基准」。两边的配置都保存，切换时不丢另一边。评级只用当前生效的一边
* 静态基准日均 = 该产品金额 ÷（该档预期月数 × 30）。产品金额取需求商品金额，不按门店拆。预期时长跟产品走，按月分档，档位可增删，默认 3、6、9、12 个月。每一档各有一个值。需求评级只用该产品对应的那一档。同一产品有多笔不同商品金额时，按该需求自己的商品金额取档
* 动态基准日均 = RBT门店的已结款合计 ÷ 对应营业天数总和。已结款是该产品下门店已经到账核销的金额，含提前支付，不含已冻结和在途。已完成的需求只计入已经到账的部分。营业日按各门店分别计数后相加，同一门店同一天只算 1 天，不同门店同一天分别计算。没有已结款时基准展示「—」。每个营业日重算一次，不能手改
* 未达到关注条件的等级是正常

评级先看异常，再看预警，再看关注。多档同时命中取更重的一档。规则可按产品单独配置，未单独配置的产品用共用阈值。每一档单独选择条件关系。

* 「或」：连续未付款天数、日均付款额低于基准的比例，满足一个即命中
* 「且」：两个都要满足

低于基准的比例是日均付款额比基准低多少。比例越大，日均付款额比基准越低。命中条件是「单店日均付款额 < 基准日均 ×（1 − 该百分比）」。这是和基准比，不是合同完成百分比。关注、预警、异常逐级加重，所以这个比例必须递增。默认 33、60、80，分别对应日均不到基准的 67%、40%、20%。

有营收并开始给贸易商、冷丰、服务商结款后，即拿日均付款额和基准比。还没有营收、尚未开始结款时不评级。页面仍展示算出来的金额和当前生效基准。未达到关注条件的等级是正常，不发异常提醒。

风控评级关闭后，全部记正常。异常付款数据为空。每日付款的金额不变。

关注为连续 1 天，或日均付款比基准低 33%。预警为连续 3 天，或低 60%。异常为连续 7 天，或低 80%。提醒句沿用原来的三档。

异常提醒由这些内容接成一句：门店、需求单号、命中的连续天数或「日均付款低于当前生效基准」、剩余付款额，再接该档配置的提醒句。正常不提醒。

首页、付款列表、付款详情、异常付款数据里的已付款金额、剩余付款额、日均付款额、生效基准、付款风险等级用这一套。已完成在付款列表和付款详情改为 1.7 的完成口径，日均付款额和生效基准展示「—」。

命中关注、预警、异常后进入工单。同一需求、同一风险事件归成一条。关闭后再次命中，另记一条。状态为待处置、处置中、已关闭。风控看全部并可处置。业务只处置本事业线。财务看金额，不改风险结论。工单不拦截新建需求。

### 1.13 风控配置

* 保存：只更新这条工单，提示「已记录处置」，关闭抽屉并刷新列表。不改每日付款，不改需求状态，不拦截新建需求。财务身份不显示保存
* 取消、关闭、点遮罩：不保存

### 1.15 门店端付款

入口在丰银宝门店端的 RBT 菜单内，底栏「付款」。只看需求门店为当前门店、状态为门店付款中或已完成的需求。

页头汇总：

* 剩余应付金额：这些需求的剩余应付合计，千分位。计算仍是含加价实付减已付款
* 预计应付金额：按次日佣金预估的下一天应还。没有每日付款时展示「未计算」。没有未完成需求时展示 ¥0.00。不要和已经发生、只是结算单未定的那一天混用
* 已付金额：这些需求的已付款合计
* 提前支付：没有剩余应付大于 0 的需求时置灰
* 说明：每天将从营业收入自动扣款。预计应付是次日佣金预估

列表每条：单号和商品包名称、付款阶段、总金额、已付款、剩余应付金额。付款中再展示「预计应付金额 ¥金额（次日预估）」。已完成不展示预计应付。无数据：暂无付款中的合作。

点进付款明细。页头为单号、付款阶段、总金额、结算周期、结算方式。页签「基础信息」「每日付款」。

基础信息，有每日付款时：

| 字段 | 取值 |
| --- | --- |
| 贸易商 | 需求上的贸易商。无值「—」 |
| 付款计划 | 已按日产生 |
| 计算来源 | 按营业流水计算 |
| 预计应付金额 | 付款中为次日佣金预估。已完成为「无」 |
| 应付款 | 已到账核销的自动扣款应付款合计。不含提前支付，不含已冻结和在途 |
| 已付金额 | 1.7 |
| 剩余应付金额 | 1.7 |
| 创建时间 | 需求创建时间。没有则不展示这一行 |
| 确认签约 | 日志里最早一条确认签约的时间。没有则不展示 |
| 付款时间 | 贸易商货款支付完成时间。没有则不展示 |
| 付款完成 | 仅已完成且已有完成时间时展示 |
| 签署合同 | 已签署的销售合同名称，可点开。没有则「—」 |

还没有每日付款时：付款计划为「未激活」，计算来源为「还没有营业流水」，预计应付金额为「未计算」，应付款为「未产生」。已付金额、剩余应付金额仍按 1.7。

每日付款从新到旧。同一天已入账的 POS、商城、直播合成一条，渠道写「当日支付」，营业流水和收入所得相加，不展示渠道结算比例。POS 收入所得是经营流水扣除平台服务费。提前支付仍单独成行。每行展示月日、当日支付或提前支付、已付款或待结算、结算时间、支付金额。当日支付再展示营业流水、收入所得、支付方式。还没到账的一天记「待结算」。点开后展示结算时间、支付方式、支付金额，以及 1.6 的门店构成：货款（含加价）、服务费（冷丰 + 服务商）。无数据：暂无每日付款。付款计划未激活，比例付不预造每日金额。

门店只看已签署、且自身为签署方的销售合同。采购合同不展示。

### 1.16 贸易商端收款

按接单时间从新到旧。没有接单时间时按更新时间。

卡片：需求单号、付款阶段、门店、应收、已结款、待结款。已完成标签为完成色，已作废和已驳回为灰色。顶部汇总笔数、应收、已结款、待结款，口径见 1.8。汇总是浅底通栏，和下面的付款卡片分开；列表上移时汇总吸在页头下方。

结款不按渠道拆开。各渠道佣金先进入门店钱包，结款从佣金余额支付，同一天可以多渠道混合后还款。PC 每日付款仍按渠道分开统计，本页不跟 PC 拆行。无数据：暂无结款明细。状态和时间见 1.8。卡片上方说明：各渠道佣金先进入门店钱包。结款从佣金余额支付，同一天可以多渠道混合后还款。

* 同一天已入账的 POS、商城、直播合成一张卡。标题为「月日 · 当日支付」。结款状态见 1.8
* 卡片中部是营业额和支付方式。支付方式固定「营业收入」。营业额把当天各渠道相加。营业额在左，数字加大；支付方式在右

* 汇总：所选区间的门店营业额、累计收入
* 渠道拆分：营业额与收入均按 **POS、直播、商城** 分列；提前支付不计入渠道营业额与收入
* 单日查看：点击趋势图圆点，下方展示该日合计及三渠道拆分；可清除单日回到默认
* 经营曲线：按日展示营业额、收入双折线；可切换全部／POS／直播／商城
* 已结束：经营数据冻结至本笔最后营业日，不再跟踪该门店后续营业与收入。历史仍可查看、不做导出

### 1.17 服务商端收款

服务商不接单、不确认签约、不付货款、不签销售合同和采购合同。

### 1.18 合同

确认签约且余额足够时生成两份，并在同一步冻结本单商品金额。规则见《贸易商接单流程PRD》。

* 销售合同：需求门店与贸易商
* 采购合同：贸易商与冷丰供应链

门店付款明细只列出已签署的销售合同。贸易商资金明细列出已签署的销售合同和采购合同。服务商不提供合同入口。合同正文只读。没有正文时展示「暂无合同正文」。

## 4. 验收标准

共用口径：

* 比例付以外的需求不产生每日付款，不产生三方应收
* 待付款及之前的需求不在付款列表、不在收款列表、不在首页当前付款中
* 未发生的日期不出现在每日付款
* 页面文案中不出现借贷类用词

各方应收与拆分：

* 商品金额 ¥750.40、门店系数 1.60、贸易商系数 1.20、没有服务商时，门店实付 ¥1,200.64，贸易商应收 ¥900.48，冷丰实得 ¥300.16，服务商应收 ¥0.00
* 该单没有确认服务商时，服务商收款页看不到它，服务商计提留在冷丰实得
* 一笔 ¥100.00 提前支付拆成贸易商 ¥75.00、冷丰 ¥25.00、服务商 ¥0.00。三笔之和等于 ¥100.00
* 门店点开这 ¥100.00，明细为货款 ¥75.00、服务费 ¥25.00。服务费是冷丰和服务商合计，两项之和等于 ¥100.00
* 自动扣款一行的贸易商、冷丰、服务商结款之和等于该行实际付款
* 提前支付的尾差不并进营业日。营业日尾差落在最近一个已发生营业日

每日付款与提前支付：

* 自动扣款的支付方式为「营业收入自动扣款」，计算来源为「获准营业事实」
* 提前支付的渠道为「提前支付」，计算来源为「提前支付」，支付方式为支付宝或微信，营业流水和结算比例为「—」
* 提前支付不替换同一天的自动扣款，两行都在
* 付款中，还没到账的批次不是已付款，结算时间和结款时间为未执行或「-」。已经到账的批次为已付款、已结款，时间是实际到账时间
* 提前支付支付成功后立即核销，结款状态为已结款，结款时间是实际支付时间
* 金额超过剩余付款额时不能支付成功。未设支付密码不能进入密码页。关闭密码层不产生付款行
* 连续 4 次密码错误锁定当日，锁定后再付不产生付款行

整单：

* 剩余付款额 = 总金额 − 已付款金额，小于 0 时为 0
* 剩余付款额为 0，且没有待冻结、在途或未完成冲正时，付款阶段为已完成，并释放额度
* 已完成的已付款金额等于总金额，剩余付款额为 ¥0.00，日均付款额和付款风险等级为「—」
* 已完成后，没到账的批次不改记已付款
* 同一笔付款中需求，在首页、付款列表、付款详情上的已付款金额、剩余付款额、日均付款额、付款风险等级一致

结款：

* 付款中待结款 = 应收 − 已结款。已结款只计已经到账的份额，含提前支付拆给该方的金额，不含已冻结和在途
* 结款明细里的待结款行，只等于还没到账的那一天拆给该方的份额，不等于卡片上的待结款
* 已结束时不把已结款改成应收。待结款仍是应收减已到账金额
* 已结束的结款明细仍只列已发生份额。已到账为已结款，没到账仍是待结款，不补差额行
* 贸易商收款的付款中不出现待确认签约、待签署、待付款
* 服务商只看到确认到自己名下的需求。基础信息是创建时间，没有接单时间和支付时间
* 服务商档案状态不是正常时不能登录

风险：

* 单店日均付款额 =（已确认营业日的实际付款合计 + 提前支付）÷ 已确认营业日天数。静态基准日均 = 该产品金额 ÷（该档预期月数 × 30），不按门店拆。动态基准日均 = RBT门店的已结款合计 ÷ 对应营业天数总和。已结款是已经到账核销的金额，含提前支付，不含已冻结和在途。比较用未四舍五入的计算值。页面写明当前生效的一种，数值不能手改，数值旁边不再重复口径
* 缺报、已冻结、在途不进入连续未付款，也不进入日均的分子和分母。确认实际为 0 的营业日才算未付款
* 低于基准的比例按关注、预警、异常递增。默认 33、60、80
* 首页不出现评级公式
* 贸易商结款明细同一天多渠道合成一笔，支付方式为营业收入。PC 每日付款仍按渠道分行
* 有营收并开始给各方结款后，即拿日均付款额和基准比。还没有营收时不评级
* 多档同时命中时取更重的等级。关闭风控评级后异常付款数据为空，每日付款金额不变
* 重置后未保存，首页和异常付款仍用保存前的阈值
* 当前台账与首页同一笔需求的连续天数、剩余付款额、日均付款额一致
* 持续未付款样例不改变每日付款的实际付款
* 处理状态保存后只改变处理记录，需求状态和每日付款不变，新建需求不受拦截
