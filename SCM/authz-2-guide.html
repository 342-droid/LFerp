菜单权限 2.0 使用说明

接口要什么权限，从写在代码里改成了配置决定：接口上只保留无参 @RequiresCapability 表示需要鉴权，归属由能力目录和原子权限决定，改权限不再需要发版。

一图看懂

四层逐级包含；一个人的权限来自岗位授权，再被当前组织已开通的业务收窄，最后在接口上按原子判定。

产品 / 运营怎么配置权限

一个人能做什么，由「岗位勾了哪些标准能力」决定，再被「所在组织开通了哪些业务」兜底收窄。超级管理员不受限。

四个概念

概念是什么例子在哪配
组织能力一个组织开通了什么业务STORE_MGMT 门店经营、WAREHOUSE_MGMT 仓储能力目录 › 组织能力
标准能力岗位授权时勾选的那一项，运营看到的就是它的中文名commerce.order.manage 订单管理能力目录 › 标准能力；角色管理 › 能力授权
原子权限一个具体动作（按钮或接口组），只属于一个标准能力mallProduct:changeStatus 商品上下架原子权限配置
接口后端的一个 HTTP 方法 + 路径POST /fulfillment-core/wms/area/create原子权限配置 › 覆盖的后端接口

判定规则：用户的权限 = 岗位上的标准能力 + 勾选的按钮，再与当前组织已开通的组织能力取交集；接口要求的原子里任意一个满足即放行。同一个岗位放到没开通该业务的组织，会自动降权，这是设计，不是 bug。

四个页面（都在「系统管理」下）

页面用来做什么要点
角色管理 › 能力授权页签给岗位勾标准能力按所属域分组显示；保存、停用角色后，在线用户的权限立即重算，不用重新登录
能力目录维护标准能力与组织能力；查看并调整一个能力下挂了哪些原子、菜单和按钮「关联管理」可认领候选原子、绑定菜单；停用能力前会校验它下面还有没有原子，停用后持有人立即失去该能力；组织能力只有超级管理员能新增、修改、停用
原子权限配置新增或编辑原子：码值、名称、唯一父能力、组织能力、使用端、覆盖的接口接口从自动扫描的清单里选，不手填；「接口核对」页签列出未被覆盖或映射失效的接口；点「保存并立即生效」后不需要发版
会话管理强制全员下线只有 SUPER_ADMIN 能执行，执行人自己也会被登出；属于运维动作，不在日常使用

常见场景

  1. 新岗位授权：角色管理 › 能力授权，勾选能力并保存 → 用户管理里把该角色绑给人 → 对方刷新页面即可看到菜单。给在线用户绑、摘角色，停用角色，停用能力，都会立即重算对方的权限，不用重新登录。
  2. 调整某个按钮或接口归谁管：原子权限配置里改原子的父能力，或增减它覆盖的接口 → 保存立即生效。
  3. 有人反馈「没权限」：403 提示里会带出所需的能力码 → 能力目录搜这个码，确认归属 → 给对方岗位勾上。
  4. 组织开通新业务：在组织上开通对应的组织能力；这个组织下各岗位能用的能力范围会跟着放大。
  5. 新增一种组织能力（仅超级管理员）：能力目录 › 组织能力 › 新增。新建后自动开通给平台根组织，平台侧岗位立即可用；其他组织要在组织上单独开通。码以 _MGMT 结尾的组织能力会沿组织树向下继承，开在平台根组织上等于所有下级组织都拥有，命名前先想清楚。
当前还没有「权限检查器」页面（查某人为什么没权限），排查暂时按场景 3 人工查。

开发写代码时怎么做

新接口写无参 @RequiresCapability，再在种子里给它配原子；业务代码要判断权限时读 UserPermissionReader，绝不读 LoginUserInfo.getPermissions()，它现在永远是空的。

接口的三种鉴权模式

写法模式权限从哪来什么时候用
@RequiresCapabilityDYNAMIC 配置驱动原子权限配置里覆盖该接口的原子，任一满足即放行新接口默认用这个
@RequiresCapability(Capability.Codes.X)DECLARED 代码写死注解参数，配置页改了也不生效存量接口过渡期；不要新增
不加注解PUBLIC 公开不鉴权确实公开的接口，并登记到 scripts/endpoint-capability-exemptions.txt
无参注解的接口如果没有任何原子覆盖，一律 403。拿不到配置就拒绝，不会放行。securityLevel（Token 存活校验）与权限归属无关，继续写在注解上。

新增一个受控接口

  1. Controller 方法上加无参 @RequiresCapability。
  2. 在 system-core/src/main/resources/db/seed/common/R__permission_atom.sql 里加一行原子映射：方法 + 路径挂到已有原子；或新建原子（码值就是按钮的 sys_menu.identity），并在 R__capability_atom.sql 里登记它属于哪些能力（可多个）。
  3. 本地启动 system-core（需要 FLYWAY_ENABLED=true），确认日志 [ApiPermission] 配置快照已发布，再到「原子权限配置 › 接口核对」确认这个接口不在未覆盖列表里。
  4. 路径禁用 @PathVariable：接口标识是静态的「方法 + 路径」。
种子是 ON DUPLICATE KEY UPDATE 的声明式终态：内容一变就会整体重跑，覆盖页面上对同一原子的修改。影响全环境的归属调整请改种子，不要只在页面上改。

业务代码里判断权限

private final UserPermissionReader userPermissionReader;

List<String> perms = userPermissionReader.permissionsOf(
        String.valueOf(user.getUserId()), user.getPrimaryOrgId());
boolean canManage = perms.contains(Capability.Codes.COMMERCE_STORE_MANAGE);
  • 权限存在 Redis authz:user:perms:{userId}:{orgId}，按「用户 + 组织」一份，每次请求读一次，不做本地缓存。
  • 读不到或 Redis 抖动时返回空集合，结果是拒绝，不会报 500。
  • 合并 dev 时已把 9 处直接读会话权限的代码改掉（审批、直播、进件审核、业务标签、运费报表）。Code Review 时看到新的 getPermissions() 读取要拦下。

单元测试怎么写

要测的用什么
某个无参接口被哪些能力守着（system-core）PermissionSeedFixture.capabilitiesGuarding(Controller.class, "method")，直接解析种子文件，不连库
同上（fulfillment / settlement 等其他服务）本模块测试包里的 CompatSeedCapabilities.guarding("GET", path)
服务内的权限分支注入 SessionStylePermissionReader，沿用在 LoginUserInfo 上写权限的旧写法；或 mock UserPermissionReader，返回 UserPermissionBundle 而不是 null

框架层（kernel 0.4.33）做了什么

  • @RequiresCapability 支持无参，由 DynamicPermissionResolver 解析所需权限；类级注解改用 findMergedAnnotation，堵住了继承场景的放行漏洞。
  • 权限来源抽成 UserPermissionSource SPI，业务侧用 Redis 实现。
  • 超级管理员在切面里直接放行。
  • 包含 grpc 租户上下文修复（0.4.32，PR !39）。

前端 + 后端前后端配合使用说明

前后端对接一个新功能时，权限要和接口一起交付：后端交接口时带上它归哪个原子，前端交页面时带上每个按钮的权限码，联调用非超管账号走查，没有 403 才算对接完成。

一个新功能从开发到上线

阶段后端前端这一步交付什么
1. 定方案列出新接口：方法 + 路径，标明哪些是页面读接口、哪些是按钮写接口列出页面上的按钮，给每个按钮定权限码 <实体>:<动作>一张「按钮 / 页面 → 接口 → 原子」对照表，写进开发计划；产品确认每个原子归哪个标准能力
2. 写代码新接口加无参 @RequiresCapability；在 R__permission_atom.sql 补原子与映射行按钮加 v-permissions="{ permission: ['<权限码>'] }"；新菜单 / 按钮在 sys_menu 种子里登记，identity 与权限码一致代码 + 种子在同一个 PR 里
3. 自查对页面跑一次 /authz-map，对照缺口表补齐；本地开 FLYWAY_ENABLED=true，看「接口核对」没有未覆盖接口缺口表里没有「缺映射」
4. 联调建一个只勾了该能力的测试角色，用非超管账号把页面和每个按钮走一遍；出现 403 按下表分工处理非超管走查无 403
5. 提测提测说明里写明：新增了哪些原子、挂在哪个能力下、测试账号需要勾哪个能力测试同学能直接按说明配角色

对接约定

  • 按钮权限码 = 菜单按钮的 identity = 原子码，三者是同一个值，格式 <实体>:<动作>，如 supplier:create。
  • 页面读接口（列表、详情、下拉选项）挂到页面的读原子，一般是 <实体>:list；不要挂到某个按钮上，否则没勾那个按钮的人连页面都打不开。
  • 公共接口（字典 /system-core/v1/dict/*、通用下拉、文件上传）不要挂到业务能力下：要么登记为公开接口，要么归入人人都有的基础能力。
  • 一个原子可以属于多个能力。同一个按钮要被两类岗位使用时，把它关联到两个能力下即可，不要拆成两个按钮、两个权限码。归属登记在 R__capability_atom.sql，sys_permission_atom.parent_capability_code 已废弃。
  • 路径禁用 @PathVariable：原子映射按静态的「方法 + 路径」匹配。
  • 前端不要用「接口 403」来隐藏按钮：按钮显隐由 v-permissions 控制；403 只是兜底。

联调遇到 403，谁来处理

403 提示 / 现象原因谁处理
提示带了所需能力码，测试账号没勾这个能力测试角色配置不全联调的人自己给测试角色勾上
接口是无参注解，但「接口核对」里显示未覆盖后端漏配原子映射后端补 R__permission_atom.sql
按钮能看到，点了 403按钮的原子没覆盖它调用的接口，或前端调了别的接口前后端对一下 /authz-map 的缺口表
按钮看不到，但接口能通按钮没加 v-permissions 或权限码与 identity 不一致前端
改了配置页不生效该接口是代码写死的 DECLARED 模式后端决定是否改成无参注解（单独改造，不在联调里顺手做）

# authz-map：页面 → 接口 → 原子 映射生成

菜单权限 2.0 里，接口用无参 `@RequiresCapability` 表示「需要鉴权」，需要什么权限由 `sys_permission_atom`（原子）和 `sys_permission_atom_api`（原子 → 接口）决定。**无参接口没有任何原子覆盖 = 一律 403**；用超管自测永远发现不了，因为超管在切面里直接放行。

本技能把「研发对接一个页面后，手工去查这个页面调了哪些接口、再去配原子」这件事变成：给出页面 → 输出缺口表 + 种子草稿 → 研发审一遍。

## 仓库与关键位置

| 用途 | 路径 |
|---|---|
| 前端页面 | `octopus-admin/src/views/**`（菜单 `sys_menu.component` 指向这里，如 `system/sessionAdmin/index` → `src/views/system/sessionAdmin/index.vue`） |
| 前端手写接口 | `octopus-admin/src/api/*.ts`：`request({ url, method, module: apiModuleMap.xxx })`，前缀拼接在 `src/utils/request.ts` |
| 前端生成 SDK | `octopus-admin/src/sdk/<service>/*.ts`：`apiClient({ url, method })`，url 已是完整路径 |
| 模块前缀表 | `octopus-admin/src/config/net.config.ts`：如 `systemCore: '/system-core'`、`commerceCore: '/commerce-core/v1'` |
| 按钮权限码 | 页面里的 `v-permissions="{ permission: ['supplier:create'] }"`；码值 = `sys_menu.identity` = 原子码 |
| 后端接口 | `octopus-cloud/<service>/src/main/java/**/controller/**Controller.java` |
| 原子与映射种子 | `octopus-cloud/system-core/src/main/resources/db/seed/common/R__permission_atom.sql` |
| 存量兼容映射 | 同目录 `R__permission_atom_compat.sql`（`legacy:<svc>:<Controller>:<capability>` 原子） |
| 能力目录种子 | 同目录 `R__capability_catalog.sql` |
| 公开接口豁免 | `octopus-cloud/scripts/endpoint-capability-exemptions.txt` |
| 静态提取脚本（参考） | `octopus-admin/scripts/extract-page-endpoints.mjs`（只跟一层 import、无 HTTP 方法，只作对照） |

先确认两个仓库所在分支（`git -C <repo> branch --show-current`），以权限 2.0 分支或已合入它的 dev 为准；分支不对就停下来告诉用户。

## 输入

用户可以给：页面文件路径、菜单路由（如 `/system/session-admin`）、菜单中文名、功能描述，或一批页面。拿到菜单名或路由时，在 `octopus-cloud` 的 `R__menu_*.sql` 种子里反查 `component`，再定位 `.vue` 文件。

## 第一步：收集页面会调的接口（前端，递归）

对每个页面：

1. 读页面 `.vue`，并**递归**读它 import 的本地组件（`./components/*`、`@/views/**`、弹窗、抽屉、Tab 子组件），直到不再出现新的本地组件。不要只看一层。
2. 收集所有被调用的 api / sdk 函数，进对应文件读出 `url` 和 `method`：
   - `src/api`：有 `module` 时，完整路径 = `net.config.ts` 里该模块前缀 + `url`（`request.ts` 第 237 行起）；没写 `module` 的，`url` 本身就是完整路径。
   - `src/sdk`：`url` 即完整路径，`method` 统一转大写。
   - 模板串里带变量的 url：列出来，标「动态 url，需人工确认」。
3. 按**触发时机**分组：
   - **页面读接口**：`onMounted` / `created` / 初始化 / 列表查询 / 字典与下拉选项加载。
   - **按钮接口**：在按钮点击处理函数（以及它打开的弹窗提交）里调用的接口，归到该按钮的 `v-permissions` 码下。按钮没有 `v-permissions` 的，标「按钮无权限码」。
   - 只在某个条件分支里才调的，标「条件调用」。

## 第二步：对照后端（注解模式 + 种子覆盖）

对每个「方法 + 路径」：

1. 在对应服务的 Controller 里找到方法（`@RequestMapping` 类前缀 + 方法 `@GetMapping`/`@PostMapping`）。找不到 = 前端调了不存在的接口，单列出来。
2. 判定鉴权模式：
   - 无参 `@RequiresCapability` → **DYNAMIC**，需要原子覆盖；
   - 带参 `@RequiresCapability(Capability.Codes.X)` → **DECLARED**，权限写死在代码里，配置不生效，记下声明的能力码；
   - 无注解 → **PUBLIC**，核对是否在 `endpoint-capability-exemptions.txt`，不在就报警（疑似漏加注解）。
3. 在 `R__permission_atom.sql` 和 `R__permission_atom_compat.sql` 的 `sys_permission_atom_api` 里 grep `'<METHOD>', '<path>'`，列出已覆盖它的原子及其父能力。
4. 按钮的权限码：在 `sys_permission_atom` 里查是否已有同码原子、父能力是什么、父能力是否还在 `R__capability_catalog.sql` 里（父能力已删除 = 孤儿原子，单列）。

## 第三步：输出

### 1）缺口表（每个页面一张）

| 触发 | 方法 | 路径 | 模式 | 已覆盖原子（父能力） | 结论 |
|---|---|---|---|---|---|

结论只用这几种：`已覆盖` · `缺映射（会 403）` · `DECLARED 不受配置管` · `PUBLIC 未登记豁免` · `后端不存在` · `待人工确认`。

### 2）种子草稿（只针对「缺映射」）

- 页面读接口：优先挂到页面已有的读原子（如 `<entity>:list`）；没有就提议新原子 `<entity>:list`，父能力取该页面菜单在 `sys_menu_capability` 绑定的能力。
- 按钮接口：挂到按钮自己的原子（码 = 按钮 `v-permissions` 码）；原子不存在就同时生成原子行，父能力取所在页面菜单绑定的能力。**页面绑了 0 个或 2 个以上能力时不要猜**，列为「待产品确认归属」。
- 公共接口（字典 `/system-core/v1/dict/*`、通用下拉、文件上传等几乎每页都调的）：**不要挂到某个业务能力下**，单列建议「登记为公开接口」或「归入人人都有的基础能力」，由用户决定。
- id 沿用文件内号段：取 `R__permission_atom.sql` 对应 INSERT 段当前最大 id + 1 递增；生成后 grep 全部 `db/seed` 确认不撞号（菜单 ID 撞车曾导致整行被覆盖、菜单凭空消失）。
- 格式与文件现有行一致：
  ```sql
  -- sys_permission_atom
  (<id>, '<code>', '<模块 / 页面 / 按钮>', '<parent_capability_code>', '<ORG_CAPABILITY>', '按钮派生', '管理后台', 1),
  -- sys_permission_atom_api
  (<id>, '<atom_code>', '<METHOD>', '<path>'),
  ```

### 3）给研发的下一步

- 种子行粘贴进 `R__permission_atom.sql` 对应段落（**先问用户，确认后再改文件**）；
- 后端新接口确认用的是无参 `@RequiresCapability`；
- 本地 `FLYWAY_ENABLED=true` 重启 system-core，看日志 `[ApiPermission] 配置快照已发布`，到「原子权限配置 › 接口核对」确认未覆盖列表里没有这些接口；
- **用只勾了该能力的非超管测试账号**把页面和每个按钮走一遍，确认没有 403。

## 红线

- 只读分析 + 生成草稿。不连数据库写数据，不自动改种子文件，不提交代码；改文件前必须得到用户确认。
- 静态分析是建议，不是事实：动态 url、条件调用、跨组件事件触发的请求都可能漏。输出里必须写明「已用浏览器 Network 抓包或测试账号走查核对」之前不算完成。
- 不替产品决定归属：一个接口挂到哪个能力是业务判断，拿不准就列出候选让用户选。
- 发现 DECLARED 接口不要顺手去参，那会改变该接口的权限来源，属于单独的改造。
