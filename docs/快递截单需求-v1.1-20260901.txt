一、先说清楚：在纠正什么

生产和售后容易把「有没有门店订货单 / shipment_plan_id」当成「有没有截单」。
代采仓配、零售自提走门店订货汇总时，截单确实会生成门店订货单，这个判断很多单碰巧对。
零售快递直发（快递截单页配的那种）不进仓储、不走采购、不生成门店订货单。
如果售后仍用 shipment_plan_id != null 猜截单，快递直发单永远像「没截单」，取消和退款规则会错。

门店订货单只是某几种履约跨过截单边界后的业务凭证，不是截单事实本身。
截单事实要落到订单自己的统一边界上。有「预计接单时间」或其它明确标志，优先用这些判断；有没有门店订货单退居二线，只作来源凭证。


二、统一截单边界（所有订单共用）

订单上要有统一截单状态，不要各模块自己猜单据。

状态：
1. PRE_CUTOFF（截单前）：还没对外形成履约承诺，可以走普通取消。
2. CUTOFF_COMMITTED（已截单）：已对外承诺要履约，不能再走普通取消；退款走售后审核流。
3. CUTOFF_RELEASED（必要时）：截单被释放 / 回退，重新按截单前规则。

语义只有一句：跨过这条边界 = 平台已经对用户、供应商或仓配承诺「这单要履约」，不能当没承诺过。

取消、退款、售后、核销门槛，只读这个状态。
这些模块不许再认识 ShipmentPlan、门店订货单、采购单、出库单。
shipment_plan_id、订货单号、采购单号只能当「怎么跨过来的」凭证，不能当「是不是已经截单」的事实源。


三、策略只负责「怎么跨」，不负责「跨了之后别人怎么认」

策略维度不是「零售 / 代采」二选一，至少是：

订单类型 × 履约方式
即：零售仓配、零售直发、代采仓配、代采直发。

每一种策略只回答三件事：
1. 什么时候跨过边界（到点、到预计接单时间、人工点截单、未截单提前发货时由系统补截单等）。
2. 用什么业务凭证证明跨界（预计接单时间、截单批次号、门店订货单、采购单、出库单、运单号等，按方式不同）。
3. 跨界后生成什么履约单据（门店订货单 / 采购单 / 出库单 / 直发待揽，按方式不同）。

四种方式触发可以不同，最终都写入同一个订单截单状态。
不要和「什么是零售、什么是代采」缠在一起讨论。差异来自履约方式：什么动作算对外承诺。


四、三段履约可以跳过，对外承诺不变

履约可以拆成三段：供应商到仓、仓到店、店到人。
有的业务会跳过其中一段（例如零售快递直发不进仓、不到店）。
跳过哪一段，只影响后面生成什么单据、仓库和门店做什么。
对用户对外的截单承诺不变：一旦进入 CUTOFF_COMMITTED，取消和售后都按已截单，不因少了一段履约就当没截单。


五、对客主状态（B / C 名称必须一致）

不要把「截单」做成对客主状态档。后台可以留「截单前 / 已截单」作事实源，客服和用户看见的词是待接单 / 待发货。
对客用「待接单」，不要写「待商家接单」（商家指谁不清）。

主状态链：

待支付 → 待接单 → 待发货 → 待收货 / 待提货 → 交易成功 / 交易失败

含义：
1. 待支付：未付款。
2. 待接单：已付款，且仍在截单前（PRE_CUTOFF）。平台还没对外承诺履约，用户可普通取消。
3. 待发货：已截单（CUTOFF_COMMITTED）且尚未发出。平台已对外承诺履约，不能再普通取消；退款走售后审核。
4. 待收货 / 待提货：货已发出或已到提货点。零售自提里，门店待收货在用户侧仍展示「待发货」，门店收货入仓后转「待自提」。这条既有展示规则不变。

直播订单、商城订单都属于零售订单，列表 / 筛选 / 导出 / 详情同一套，不单开规则。
后台与 C 端主状态必须同步，不能 C 端写待接单、B 端仍写待发货。


六、未截单提前发货：系统当场补截单，并一次完成接单 + 发货

正常路径（走截单配置时间）：
付款 → 待接单（截单前）→ 到配置时刻自动截单 → 待发货（已截单）→ 发货 → 待收货。

例外（不走截单配置时间）：
订单仍在截单前（待接单 / PRE_CUTOFF），履约侧提前发货（上传快递单、回传运单、仓配出库等现有发货动作）。

此时系统在发货当口必须同时做完三件事（底层一次落库，页面不另做「补截单 / 接单 / 发货」展示）：
1. 对该订单补一次截单动作，写入 CUTOFF_COMMITTED。这条补截单由发货事件触发，不是等到快递截单页或门店订货汇总的配置时刻。
2. 订单状态同时完成【接单】和【发货】，对客主状态直接变为「待收货」（自提按既有规则进入对应待收货 / 待提货）。中间不停留「待接单」，也不经过「待发货」。
3. 之后取消 / 退款 / 售后一律按已截单处理。

原因：货已经发出，对外承诺已经事实发生；配置时刻的自动截单只处理「到点仍未发」的待接单，管不到已经发出去的单。
这是底层逻辑，无需在页面呈现，不新做进度条、不新做发货交互。现有发货入口怎么用还怎么用，页面上只看到状态变成待收货。


七、和快递截单页的关系

快递截单页（mdm_order_express_cutoff.html）配的是：零售 × 直发（快递到家，供应商直发）。
它决定零售快递直发「什么时候跨边界」（每天某个时刻，截上一窗待接单、未填快递单的已付单）。
到点截单后：订单写入 CUTOFF_COMMITTED，对客主状态从「待接单」变为「待发货」；用户 APP 取消订单隐藏，申请退款走售后审核。
本页不生成门店订货单，这是对的，但不能因此认为这些单「没有截单」。

若零售快递直发单在配置时刻前就提前发货：走第六条，由发货事件当场补截单并一次完成接单 + 发货，状态为待收货；不要等本页配置时刻再截。

本页配置范围本期仍是零售快递直发；不要把本页改成四种履约的总配置台。总原则在订单域，不在本页表单。
本页字段、交互、文案本期不动。


八、和门店订货汇总截单的关系

采购 → 门店订货汇总里的截单，配的是仓配类（零售仓配 / 代采仓配等）「什么时候跨、生成门店订货单」。
那也只是另一种跨法，同样要写回订单的 CUTOFF_COMMITTED，对客主状态同样从「待接单」变为「待发货」。
未截单却提前出库 / 发货，同样由发货事件当场补截单，并一次完成接单 + 发货，状态为待收货；不走本页配置时刻。

两套配置页可以继续分开，但订单上的截单状态必须是同一个字段 / 同一套状态。


九、订单管理怎么露出（本期原型只加「待接单」）

后台零售订单、代采订单：
1. 状态筛选在「待支付」和「待发货」之间增加「待接单」。
2. 状态列：截单前的已付单写「待接单」；已截单未发出的写「待发货」。
3. 详情进度条「运输中」改为「待接单」，其后增加「待发货」（快递 / 自提均有），按主状态点亮。
4. 取消：待接单按截单前规则，可普通取消。已截单的待发货按原规则，不再普通取消。
5. 发货 / 上传快递单：沿用现有入口和规则，不因待接单新做交互。未截单提前发货时，底层当场补截单并一次完成接单 + 发货，状态变为待收货；页面不另呈现补截单过程。

用户 APP：
1. 没有进度条，不要补进度条。
2. 不单开待接单页签，也不在「我的」加入口；待接单只出现在「全部」。
3. 全部列表卡片、详情标题同步写「待接单」。进货订单共用同一套列表 / 详情，同样不单开页签。
4. 待接单的按钮对齐截单前：可取消；仅退款走发货前。不要改支付成功跳转、不要改其它按钮和售后页。
5. 已截单演示单仍写「待发货」，取消隐藏（原 cutoff=after 逻辑不动）。


十、开发验收（写进需求，避免再猜单据）

1. 判断一单是否已截单：只看订单统一截单状态；可用预计接单时间等标志辅助。禁止用 shipment_plan_id != null 作为截单事实。
2. 零售快递直发：过了本页策略时刻后，即使没有门店订货单、没有采购单，状态也必须是已截单，对客为「待发货」。
3. 零售 / 代采仓配：门店订货汇总截单后，除了生成订货单，必须同时把订单写成已截单，对客为「待发货」。
4. 未截单提前发货：由发货事件当场补截单（CUTOFF_COMMITTED），不是等到截单配置时间；订单状态同时完成接单 + 发货，对客为「待收货」，不能停在待接单或待发货。此为底层逻辑，页面不另呈现。
5. 取消、退款、售后、核销：只读统一状态。有订货单只当凭证，不当判断条件。
6. B 端、C 端主状态名称必须一致：待支付、待接单、待发货、待收货 / 待提货。
7. 用户 APP 订单流有待接单状态（全部列表 + 详情标题），无独立页签、无「我的」入口、无进度条，不改其它逻辑和交互。
8. 快递截单页配置范围本期仍是零售快递直发。


十一、本期不做

1. 不改快递截单页原型（字段、交互、文案先不动）。
2. 不在本页展开代采、仓配策略配置。
3. 不把「零售 / 代采定义」写进本页需求。
4. 不把「截单」做成对客主状态。
5. 用户 APP 不补进度条；不改取消 / 退款页、支付成功跳转等其它交互。
6. 门店核销详情不改。
7. 用户 APP「配送方式」是生产已有能力，不写进本期验收。
8. 订单支付流水是另一份需求，不塞进本文。
9. 未截单提前发货的补截单 / 接单 / 发货是底层一次完成，不在页面呈现过程。
