## 一、背景与目标

### 1.1 背景

订单履约过程中，用户可发起售后。当前存在三类问题：

1. **资金与履约冲突**：售后未完结时，代采端 / 客户端 / PC 后台仍可取消整单，导致售后单与订单关闭互相覆盖，退款、补货无法闭环。
2. **列表信息不足**：订单列表只展示商品名称和订单状态，运营无法在列表直接判断「这单有没有售后、售后走到哪一步」，必须点进详情。
3. **完成后无法代发起**：订单完成后后台仅有「查看」，客诉补开售后只能走线下或让用户自行申请，与「平台退款」能力割裂。

### 1.2 目标

**业务目标**

- 避免「处理中售后 + 整单取消」并发，降低错退、漏补、客诉。
- 运营在订单列表即可识别售后结果与进度，缩短处理路径。

**产品目标**

- 任意端口取消订单时，若存在未完结售后，一律拦截并提示。
- 零售 / 代采订单列表商品名展示与详情一致的售后标识；订单状态右侧展示售后状态。
- 订单完成后后台可「发起售后」，与「平台退款」共用售后单能力。
- 零售 / 代采订单筛选在「订单状态」后增加「售后状态」。

### 1.3 范围说明

**本期包含**

- 取消订单拦截（客户端、进货/代采端、PC 零售订单、PC 代采订单）
- 零售 / 代采订单列表：商品售后标识、售后状态列
- 订单完成后后台「发起售后」
- 零售 / 代采订单筛选「售后状态」

**本期不包含**

- 不改变各端「取消订单」按钮本身的展示规则（仍按原订单状态控制是否出现）
- 不在本期扩展 C 端待自提页的取消入口

## 二、用户分析

### 2.1 目标用户

| 角色 | 端口 | 使用场景 |
|------|------|----------|
| 消费者 | 用户 APP（客户端） | 待付款 / 截单前待发货时点「取消订单」 |
| 门店进货人 | 用户 APP 进货（代采端） | 进货单详情取消订单 |
| 运营 / 客服 | PC 零售订单、代采订单 | 列表取消订单、看售后进度、完成后代用户开售后 |

### 2.2 用户痛点

| # | 痛点 | 描述 | 影响 |
|---|------|------|------|
| 1 | 售后进行中仍能关单 | 售后未结束就取消整单，资金与库存对不上 | 高 |
| 2 | 列表看不出售后 | 必须进详情才能知道商品是否退款中、整单售后到哪一步 | 高 |
| 3 | 完成后无法代开售后 | 已完成订单客诉只能口头处理，后台没有与平台退款同级的入口 | 中 |
| 4 | 无法按售后进度筛单 | 订单状态筛不到「待审批 / 退款中」等售后态 | 中 |

### 2.3 用户故事

作为运营，我希望取消订单时系统拦住处理中售后的单，以便避免错关单。

作为运营，我希望列表商品名和订单旁直接看到售后标识与售后状态，以便不用逐条点详情。

作为客服，我希望已完成订单也能发起售后，以便与平台退款一样落到售后单。

## 三、功能需求

### 3.1 取消订单拦截

**模块说明**：用户已发起且未完结的售后单，任意端口取消整单均拦截。

#### FR-CANCEL-001 拦截条件

**优先级**：P0

**描述**：满足以下全部条件时，拦截取消订单，不关闭订单、不触发退款。

| 项 | 规则 |
|----|------|
| 售后类型 | 仅退款、退货退款、补货、换货 |
| 未完结（C 端） | 售后阶段不是「成功 / 关闭 / 失败」 |
| 未完结（B 端） | 售后状态不是「已完成 / 已取消 / 已拒绝」 |
| 作用端口 | 客户端订单详情、进货（代采）订单详情、PC 零售订单、PC 代采订单 |
| 判定维度 | 整单：该订单下任意一笔符合条件的售后未完结即拦截 |

**验收标准**：

- [ ] 订单存在处理中售后时，上述任一端口点「取消订单」均被拦截
- [ ] 售后均已完结时，取消订单走原确认流程
- [ ] 拦截后订单状态不变

**异常情况**：无订单号或查不到售后记录时，不拦截（按原逻辑取消）。

---

#### FR-CANCEL-002 拦截提示（各端文案一致）

**优先级**：P0

**描述**：拦截时弹出提示框，不进入「确认取消」二次确认。

| 元素 | 文案 |
|------|------|
| 主标题 | 无法取消订单 |
| 提示文案 | 当前订单存在处理中售后，暂无法取消订单。 |
| 按钮 | 好的 |

**验收标准**：

- [ ] 客户端 / 进货端：单按钮弹窗，点「好的」或遮罩关闭，订单仍在原状态
- [ ] PC 零售 / 代采：同样标题、正文、仅「好的」，不出现「确认取消」
- [ ] 售后完结后再点取消，出现原「确认取消订单」弹窗

**异常情况**：C 端待自提本身无取消按钮，本期不新增入口；验收以有取消按钮的状态为准（待付款、截单前待发货；PC 按原取消可见规则）。

---

### 3.2 订单列表 · 商品售后标识

**模块说明**：零售 / 代采订单列表「商品信息」列 = 商品名称 + 售后标识，与订单详情「商品明细」商品名称上的标识一致。

#### FR-LIST-001 商品售后标识

**优先级**：P0

**描述**：列表「商品信息」在商品名右侧展示标识。列表只展示一行商品时，取该行对应商品的标识；「等 N 种」时取列表主商品（第一件）的标识。

**标识枚举（不得增减）**

| 标识 | 含义 | 推导规则（与详情一致） |
|------|------|------------------------|
| 退款中 | 仅退款 / 退货退款进行中 | 售后状态为：待审批、退款中、待退货、待收货、退款异常 |
| 部分退款 | 退款已完成但未退完购买数 | 仅退款 / 退货退款状态=已完成，且退货数量 < 购买数量 |
| 全额退款 | 退款已完成且覆盖购买数 | 仅退款 / 退货退款状态=已完成，且退货数量 ≥ 购买数量 |
| 补发中 | 补货进行中 | 补货状态为：待审批、待收货 |
| 已补发 | 补货已完成 | 补货状态=已完成 |
| （不展示） | 无售后，或已拒绝且无其它结果 | — |

**优先级**：同一商品同时存在多笔售后时，先看退款进行中 → 再看退款已完成 → 再看补货进行中 → 再看补货已完成。

**验收标准**：

- [ ] 列表标识文案、颜色与订单详情商品明细一致
- [ ] 无售后的订单不展示标识
- [ ] 打开同一订单详情，商品名上的标识与列表一致

---

### 3.3 订单列表 · 售后状态列

**模块说明**：零售 / 代采订单列表在订单状态右侧新增「售后状态」，表示整单当前最需处理的售后进度。

#### FR-LIST-002 售后状态字段

**优先级**：P0

**描述**：位置在「订单状态」与「操作」之间。取值与售后单状态一致，一状态一色，与详情「售后明细」状态标签一致。

**售后状态枚举（不得增减）**

待审批、退款中、已拒绝、待退货、待收货、退款异常、已完成、已取消。

无售后时展示 `-`。

**一单多笔售后时的展示优先级（高 → 低）**

1. 退款异常  
2. 待审批  
3. 退款中  
4. 待退货  
5. 待收货  
6. 已拒绝  
7. 已完成  
8. 已取消  

**验收标准**：

- [ ] 表头在订单状态右侧为「售后状态」
- [ ] 有售后时展示上表中的一个状态；无售后为 `-`
- [ ] 同时存在「仅退款·退款中」与「补货·待收货」时，列上展示「退款中」
- [ ] 核销导致售后关闭后，该行售后状态随数据刷新

### 3.4 订单完成后发起售后

**模块说明**：已完成订单后台可开售后，能力与「平台退款」相同，均生成售后单。

#### FR-AS-001 操作入口与可见性

**优先级**：P0

**描述**：PC 零售订单、代采订单操作列：

| 订单状态 | 操作文案 | 说明 |
|----------|----------|------|
| 零售自提：待收货、待提货 | 平台退款 | 保持原规则 |
| 零售快递 / 代采：待收货 | 平台退款 | 保持原规则 |
| 已完成 | 发起售后 | 本期新增 |
| 其它状态 | 不展示上述入口 | — |

两个入口打开同一侧栏抽屉（标题「发起售后」），可选仅退款 / 退货退款 / 补货，提交后生成售后单。

**验收标准**：

- [ ] 已完成订单操作列出现「发起售后」，点开抽屉字段、校验、提交与「平台退款」一致
- [ ] 待收货（及零售自提待提货）仍为「平台退款」，不改名为「发起售后」
- [ ] 已关闭、待发货等状态不出现「发起售后」

**异常情况**：抽屉校验失败（未选商品、未填原因/描述/凭证等）时不关单、不生成售后单，提示与现网平台退款一致。

---

### 3.5 订单筛选 · 售后状态

**模块说明**：零售订单、代采订单筛选，「订单状态」后增加「售后状态」。

#### FR-FILTER-001 筛选项

**优先级**：P0

**描述**：

- 位置：展开区，「订单状态」右侧（其后原有字段顺序不变）。
- 控件：下拉，默认「全部」。
- 选项：全部、无售后、待审批、退款中、已拒绝、待退货、待收货、退款异常、已完成、已取消。
- 查询：点「查询」按当前选项过滤；「重置」清空为全部。
- 匹配：与列表/详情推导出的整单售后状态一致；「无售后」匹配没有售后状态的订单。

**验收标准**：

- [ ] 零售、代采展开筛选后，订单状态后可见售后状态
- [ ] 选「待审批」只留下整单售后状态为待审批的单
- [ ] 选「无售后」只留下无售后的单
- [ ] 与支付渠道、履约方式等条件同时生效（AND）

## 五、方案设计

### 5.1 信息架构

```
订单管理
├── 零售订单（列表：商品标识 + 售后状态列；筛选：售后状态；操作：平台退款 / 发起售后）
├── 代采订单（列表：商品标识 + 售后状态列；筛选：售后状态；操作：平台退款 / 发起售后）
用户 APP
├── 订单详情（取消订单 → 拦截弹窗）
└── 进货订单详情（同上）
```

### 5.2 取消拦截流程

```
用户/运营点击「取消订单」
  → 该订单是否存在未完结售后？
      → 是：弹「无法取消订单」+「好的」，结束
      → 否：弹原「确认取消」→ 确认后关单
```

### 5.3 商品标识推导流程

```
该商品是否有仅退款/退货退款进行中？ → 退款中
否则是否有仅退款/退货退款已完成？
  → 退货数 < 购买数：部分退款
  → 否则：全额退款
否则是否有补货进行中？ → 补发中
否则是否有补货已完成？ → 已补发
否则：不展示
```

### 5.4 原型页

| 页面 | 路径 |
|------|------|
| 零售订单 | `MDM/mdm_order_retail.html` |
| 代采订单 | `MDM/mdm_order_proxy.html` |
| 用户/进货订单详情 | `user-app/h5/order-detail.html` |

## 六、数据指标

### 6.1 北极星指标

处理中售后订单被成功取消的次数 → 目标为 0。

### 6.2 过程指标

| 指标 | 说明 |
|------|------|
| 取消拦截曝光次数 | 弹出「无法取消订单」的次数（分端口） |
| 列表售后状态使用率 | 使用「售后状态」筛选的查询次数 |
| 完成后发起售后单量 | 已完成订单提交的售后单数 |

### 6.3 反指标

售后完结后取消订单成功率不应下降；平台退款提交成功率不应因入口拆分而下降。

## 九、附录

### 9.1 术语

| 术语 | 说明 |
|------|------|
| 未完结售后 | 售后尚未到达已完成、已取消、已拒绝（C 端对应 success/closed/failed） |
| 售后标识 | 贴在商品名称上的结果标签：退款中、部分退款、全额退款、补发中、已补发 |
| 售后状态 | 售后单进度：待审批、退款中、已拒绝、待退货、待收货、退款异常、已完成、已取消 |
| 平台退款 | 履约中（待收货/待提货）后台代开售后的入口文案 |
| 发起售后 | 订单完成后后台代开售后的入口文案，能力与平台退款相同 |
